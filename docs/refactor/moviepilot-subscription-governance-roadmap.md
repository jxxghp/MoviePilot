## 1. 目标

在不增加 PT 站点压力、不牺牲订阅完成正确性、不制造重复下载的前提下，解决以下问题：

1. 日常 `refresh -> match` 在订阅较多时线性变慢，即使还没有进入 24 小时兜底搜索也会影响用户；
2. 24 小时兜底搜索在全局锁内逐订阅等待和访问站点，放大日常 Match 的锁竞争；
3. RSS、爬虫 Match、手工搜索和兜底搜索缺少统一的订阅级 single-flight、提交幂等与取消终态；
4. 用户看不到排队、匹配、搜索、下载提交、失败和取消的业务状态，容易把后台失败理解为操作成功或订阅消失。

最终用户价值不是单纯缩短某个函数耗时，而是：日常资源到达后尽快完成匹配，兜底搜索不会阻塞日常
Match，同一资源不会因链路重叠重复提交，慢站点或 TMDB 故障不会拖死整轮，用户能够看到真实进度和失败。

目标常规规模明确为：`100–200` 条活跃订阅、`10–20` 个启用站点、单轮 `1000+` RSS/Spider 候选。
达到该规模时不得依赖跨刷新周期漏处理候选来缩短表面耗时，最终验收仍以正确性、站点压力和用户完成时间
共同决定，而不是只满足单个吞吐数字。

## 2. 边界

本 Goal 只按单媒体服务器场景设计和验收，不扩建多媒体服务器并发、聚合或 provider 分片。

本 Goal 不做以下事情：

- 不把 `match()` 简单改成 `async def`，也不以删除锁作为完成标准；
- 不通过跨刷新周期轮流处理订阅来隐藏耗时，因为这会漏掉短生命周期候选；
- 不把所有订阅或站点请求直接并发化；
- 不把 TMDB 详情长期缓存当成性能修复；
- 不在当前叶处理多条订阅记录指向同一媒体的产品规则；
- 不重构通用 Scheduler、TaskRegistry 或媒体服务器框架。

同步实现可以继续位于受控 worker 内，但网络、数据库和文件 I/O 不得阻塞主事件循环。订阅完成、下载事实、
洗版优先级和缺集口径继续只有一套 canonical 业务实现。

## 3. 已确认事实

### 3.1 日常路径

当前日常流程为：

```text
Scheduler / 手工刷新
        |
        v
TorrentsChain.refresh()
  RSS: 每站点读取一次 RSS
  Spider: 每站点最多抓取两页
  对新种子做媒体识别并写入本地缓存
        |
        v
SubscribeChain.match()
  获取 search/match 共用类级锁
  读取所有 R/P 订阅
  每条订阅重新识别目标媒体
  每条订阅查询媒体库缺失情况
  每条订阅扫描本轮返回的完整候选缓存
  匹配后下载、完成判定和状态写回
        |
        v
释放类级锁
```

生产 V2 `2.15.5` 的少量订阅样本显示：

| 指标 | 中位数 | 解释 |
| --- | ---: | --- |
| 单轮日常 Match | 约 `9.931s` | 不含 24 小时兜底搜索 |
| 单条订阅 | 约 `395ms` | 当前样本订阅数量较少 |
| 媒体识别与媒体库检查 | 约 `357ms` | 是当前单条订阅主要耗时 |
| 扫描约 600 条候选 | 约 `37ms` | 当前样本不是主要热点，但复杂度仍为订阅数乘候选数 |

这些数据来自生产只读日志，只能证明当前样本的热点分布，不能直接外推大量订阅的收益比例。

2026-08-24 对 NAS 上 V2 `2.15.5` 的 11 轮连续生产日志再次做了只读聚合：每轮约 12 条订阅、5 个
候选域、500 条候选，Match 中位数约 `17.752s`，范围约 `11.049–29.200s`；单订阅相邻日志跨度的
中位数约 `0.4s`，每轮 TMDB 查询日志为 `12–63` 次。该样本进一步确认日常 Match 已有明显波动，
并且候选重识别会放大外部请求；日志计数只作为 001A 基线，不替代后续同 revision 固定快照隔离重放。

### 3.2 调度与站点访问

| 来源 | 默认调度 | 单轮站点访问模型 | 与订阅数量关系 |
| --- | --- | --- | --- |
| RSS 刷新 | 默认每 30 分钟 | 每个启用站点读取一次 RSS | 不随订阅数线性增加 |
| Spider 刷新 | 每天随机 32 次 | 每个启用站点最多抓取两页 | 不随订阅数线性增加 |
| 日常 Match | 紧随 RSS/Spider 刷新 | 候选匹配主要在本地；命中后可能获取种子并提交下载 | 计算和 TMDB/媒体库查询随订阅数增加 |
| 新增订阅搜索 | 每 5 分钟检查 | 仅处理新建订阅，调用站点搜索 | 随新增订阅增加 |
| R/P 兜底搜索 | 可配置，默认间隔 24 小时且默认关闭 | 每条订阅搜索多个站点；不同关键词间再等待 1–10 秒 | 随订阅、站点和关键词近似相乘 |

站点搜索当前会并发访问不同站点，同一站点按页顺序请求。60–300 秒等待位于兜底搜索的逐订阅循环内，
并且整个搜索持有与 Match 共用的类级锁。该等待既是跨用户错峰手段，也是线性累计耗时和锁竞争来源；
不能只删除等待，也不能继续让它占用业务锁。

### 3.3 TMDB 缓存语义

日常 Match 的 `cache=False` 会同时绕过媒体识别映射缓存和 TMDB HTTP 响应缓存。它不是单纯的性能疏漏：
Match 会在完成前用新鲜季集数据修正总集数。若直接切为最长可达 24/72 小时的普通缓存，可能把仍在更新的
12/13 集剧集错误判定完成并删除订阅。

因此当前未提交候选中的 `cache=True` 不可交付，必须撤销。可优化的是“本轮怎样取得一次可信的新鲜事实”，
而不是“是否长期复用旧详情”。

### 3.4 当前结构性问题

1. 资源刷新只把新种子追加到缓存，但随后把完整缓存交给 Match；旧候选会在每轮被重复扫描；
2. Match 先为所有订阅执行 TMDB 和媒体库检查，之后才知道本轮候选是否可能命中；
3. 订阅数 `S` 与候选数 `C` 的核心循环近似 `O(S * C)`；
4. 候选获取、资源匹配、完成对账、下载提交和状态写回被包在同一个长锁生命周期；
5. 兜底搜索在锁内执行随机等待和站点网络 I/O；
6. 不同入口缺少统一订阅级 single-flight，提交前也没有明确的跨入口幂等合同；
7. 停止只能在订阅或关键词边界观察，不能可靠中断随机等待和正在执行的同步网络调用。

## 4. 不变量

任何方案必须同时保持：

1. RSS 和 Spider 的默认站点请求频率不得增加；
2. 兜底搜索的峰值每站点并发不得高于基线，出现 `429/403` 或超时时应降低压力而不是重试放大；
3. 每轮需要完成判定时必须使用足够新鲜的季集事实，不能因缓存错误完成或删除订阅；
4. 下载前必须重新读取订阅、缺集、下载历史和洗版优先级，准备阶段的快照不能直接作为提交依据；
5. 同一订阅、同一 torrent、同一季集覆盖在入口重叠时至多提交一次；
6. 失败、取消、停机和锁等待失败不能写入成功或完成状态；
7. 一条订阅失败不得阻止批次中其他订阅继续，但最终批次必须暴露聚合失败；
8. 手工刷新可以优先，但不能绕过站点预算和下载幂等；
9. 音乐订阅在缺少独立准备/提交合同前保持串行；
10. 所有优化都必须能独立关闭或回滚到稳定 V3 行为。

## 5. 方案评估

### 5.1 方案矩阵

| 方案 | 预期收益 | 站点压力 | 正确性/维护风险 | 决策 |
| --- | --- | --- | --- | --- |
| 保持全量串行，只增加日志 | 无直接性能收益 | 不变 | 用户问题继续存在 | 仅作为基线 |
| Match 全部改用 `cache=True` | 当前样本可能减少约 0.2–0.35s/订阅 | 不变 | 可能错误完成正在更新的剧集 | 拒绝 |
| 全部订阅直接开 2/4 worker | 可缩短 TMDB/媒体库等待 | Match 本身不直接增加 PT 请求，但可能放大 TMDB、媒体服务器和下载并发 | 线程安全、完成竞态、重复下载 | 不作为首选，只在前置治理后做隔离压测 |
| 候选建立媒体身份/站点/季索引 | 降低 `S * C` 本地扫描 | 不变 | 自定义词和标题兜底不能被粗索引误删 | 建议，先作为无损前置门禁 |
| 仅匹配本轮新增候选 | 显著减少重复扫描 | 不变 | 临时失败、后建订阅和旧候选重试可能丢失 | 不能单独采用，需 pending/replay 合同 |
| 新增候选优先，旧候选按有界重试账本回放 | 降低常态扫描并保留失败恢复 | 不变 | 需要候选身份、终态和 TTL | 推荐目标方案 |
| 先候选门禁，再查 TMDB/媒体库 | 没有相关候选时跳过主要热点 | 不变 | 完成对账不能随候选一起跳过 | 推荐，但必须拆出独立完成对账 |
| 单轮新鲜事实租约 | 同媒体在一轮只请求一次，不跨轮复用旧详情 | 不变 | 同媒体不同 episode group/季必须进入 key | 推荐 |
| 稳定元数据复用 + 轻量季集查询 | 可能替代每条完整详情请求 | 不变 | TMDB 返回合同、地区词和 episode group 需验证 | 优先探针，收益成立再实现 |
| 单媒体服务器单轮请求合并 | 重复目标只查一次媒体库 | 不变 | 不同订阅范围、洗版规则不能共用最终缺集结果 | 可做事实层合并，不缓存业务判定 |
| 同轮有界 2/4 worker 准备 | 隐藏独立 TMDB/媒体库等待 | 不变 | 共享缓存和同步客户端线程安全；提交顺序变化 | 候选门禁后仍慢时再启用 |
| 跨刷新周期分片订阅 | 每轮变快 | 不变 | 候选可能在轮到订阅前过期，延迟不可控 | 拒绝作为默认方案 |
| 按候选分片，同轮处理完 | 可复用候选索引，适合候选远少于订阅 | 不变 | 标题兜底和自定义词需保守回退 | 推荐的内部执行形态 |
| 兜底搜索批次只随机等待一次 | 去掉按订阅线性累计 | 峰值可能集中 | 大量实例在相近时间同时访问站点 | 不能单独采用 |
| 兜底搜索持久游标 + 每站点预算 | 不占长锁，按容量持续推进 | 可明确限制且具备退避 | 需要批次身份、恢复和公平性 | 推荐 |
| RSS/Spider 站点并发刷新 | 缩短站点获取阶段 | 提高瞬时站点压力 | PT 站点承载和风控不确定 | 默认不做 |
| 全事件驱动替代定时刷新 | 长期可减少无效工作 | 取决于上游能力 | 改动大，历史插件/站点无统一事件源 | 远期，不进入首轮 |

### 5.2 推荐架构

推荐把现有长函数拆成三个业务阶段，但不要求一次 PR 完成重构：

```text
RSS / Spider / 兜底搜索
          |
          v
候选账本与本轮 delta
  - torrent 身份、来源、站点、首次/最后出现时间
  - pending / matched / rejected / retryable / expired
          |
          v
无损候选索引与受影响订阅集合
  - 媒体 ID 可确定时直接反向定位
  - 标题兜底、自定义识别词和旧缓存进入保守集合
          |
          v
准备阶段（可取消，可选 2/4 有界 worker）
  - 本轮新鲜 TMDB 事实租约
  - 单媒体服务器事实查询
  - 规则匹配和下载计划
          |
          v
串行提交阶段
  - 重读订阅和下载事实
  - 幂等校验
  - 提交下载
  - 写入进度、优先级和完成状态
```

完成对账必须是独立路径：候选门禁可以决定“本轮是否值得做资源匹配”，但不能决定“订阅是否已经完成”。
建议将完成对账按较低频率或在媒体库/元数据变化事件后执行；它仍使用新鲜季集事实，但不扫描站点候选。

### 5.3 站点压力治理

RSS/Spider 保持现有逐站点串行刷新，不通过并发化换取几秒收益。兜底搜索从“订阅级随机休眠”改为“站点级
容量预算”：

- 每个站点最多 1 个在途搜索；
- 同一站点请求之间保留随机间隔，具体区间通过离线压测和受控生产运行指标确定，不在设计阶段拍定；
- 批次启动保留全局随机抖动，避免大量 MoviePilot 实例整点同时启动；
- `429/403`、登录失效和连续超时触发站点级冷却，不让其他订阅立即重试同一站点；
- 手工搜索可以提高队列优先级，但不能绕过站点并发和冷却；
- 站点预算由订阅域消费，首轮不扩建成全应用通用限流平台。

该设计让等待不再持有 Match/提交锁，同时比“每条订阅固定睡眠”更直接地约束真实外部请求。

### 5.4 下载防重与锁边界

锁应按事实所有权拆分，而不是按入口拆分：

1. 候选获取不持有订阅提交锁；
2. TMDB、媒体服务器和站点网络请求不持有提交锁；
3. 同一订阅的准备任务使用 single-flight 合并；
4. 下载提交使用短临界区，并在临界区内重读当前订阅、下载历史、媒体库缺失和洗版优先级；
5. 幂等键至少包含订阅逻辑身份、torrent 身份和计划覆盖的季集范围；
6. 下载器接受但本地写回失败属于“不确定”终态，不能自动重试造成重复任务，必须先对账下载器。

同媒体的多条重复订阅需要更高一层的跨记录幂等，保留在最低优先级叶，不阻断单条订阅治理。

## 7. 上线前验证与验收

### 7.1 场景

每个行为叶必须使用同一 revision、同一固定数据快照：先由当前 canonical 逻辑生成参考集合，再在隔离环境中
只运行新链路并比较结果。该流程不进入生产，也不产生真实外部请求和下载副作用。

1. RSS，无新候选；
2. RSS，少量新候选且不命中；
3. RSS，新候选命中电影、追更剧集、全集和分集洗版；
4. Spider，同样三档候选；
5. 24 小时兜底搜索无结果、部分结果、站点超时和 `429/403`；
6. 日常 Match 与兜底搜索重叠；
7. 手工刷新或手工搜索与后台任务重叠；
8. 下载器拒绝、超时或本地写回失败，并在下轮按普通订阅流程重新判断；
9. 停机、取消和进程重启后的恢复；
10. 单媒体服务器可用、慢响应和不可用。

订阅规模使用真实形态的小/中/大档，不以固定的 1/10/101 档位作为治理要求；候选数量与站点数量也要
独立缩放，避免只测订阅数量。

### 7.2 指标

| 维度 | 必测指标 |
| --- | --- |
| 用户耗时 | 刷新总耗时、首个匹配/首个下载时间、批次完成 p50/p95 |
| 本地计算 | 候选预处理、每订阅匹配、完成对账、提交耗时 |
| TMDB | 请求数、缓存/租约命中、错误率、p50/p95 |
| 媒体服务器 | 请求数、p50/p95、超时和合并命中 |
| PT 站点 | 按站点请求数、峰值在途、最小间隔、429/403/超时、错误冷却跳过数 |
| 正确性 | 命中集合、下载集合、缺集集合、完成/删除集合与基线一致 |
| 并发 | 同订阅跨 Search/Match 准入冲突数、重复下载数、准入与站点租约释放失败数 |
| 生命周期 | 取消延迟、event-loop lag、遗留 task/worker/锁、shutdown 上限 |

### 7.3 门禁

- 日常 Match 的站点请求数和峰值不得增加；
- 兜底搜索的每站点峰值在途不得超过基线，分布式错峰不能退化为整点突发；
- 所有正确性集合必须与基线一致，新增完成对账用例必须覆盖 12/13 集更新；
- 重叠入口不得产生重复下载；

- 性能收益不足以覆盖维护成本时停止对应叶，保留更小方案；
- 本地开发数据只验证可重放性，最终性能结论必须来自受控样本或生产只读证据。

## 10. 当前运行日志验收

当前日志用于上线后确认新治理链路是否健康，不承担旧新链路 A/B 对照，也不引入独立日志聚合器。日志内容遵循
现有主日志输出方式，以稳定 `key=value` 字段提供机器可检索的轮次摘要。V3 生产组合根固定注入持久搜索队列，
站点请求聚合以该治理路径为验收对象；无队列的兼容执行路径保留任务摘要，但站点字段为零值。

### 10.1 轮次摘要

- Search 与 Match 每次实际执行各输出一条 `订阅治理轮次开始` 和一条 `订阅治理轮次结束` 的 `INFO`；
- 两类摘要均包含 `operation`、`run_id`、订阅数和耗时；Search 额外包含 `batch_id` 与来源，Match 包含输入
  站点数和完整候选数；
- 结束摘要使用 `task_completed`、`task_skipped`、`task_failed`、`task_cancelled` 等任务终态字段；其中
  `task_completed` 只表示本次处理任务正常收口，不表示订阅已经下载完成或已经删除；
- Search 在队列消费、通知、批次查询或进度回调异常时仍输出配对的结束摘要，并以 `round_failed=1` 区分轮次
  编排失败与单条任务失败；
- `admission_conflicts`、`cancelled`、`ttl_timeouts` 分开计数，避免把准入跳过、用户取消和协作 TTL 超时混为
  同一种“未执行”；
- `release_failures` 汇总订阅准入与站点租约收口失败；任何单次释放失败同时立即输出 `ERROR`，不能只留在轮次
  计数里。

### 10.2 站点与候选摘要

- Search 结束摘要聚合 `sites`、`site_requests`、`site_failures`、`site_cooldown_skips`、`candidates` 和
  `cooldown_seconds`；正常成功不产生额外冷却，错误冷却和已有在途租约导致的未发请求统一计入跳过数；
- Match 的 `candidates` 表示本轮完整候选快照数量，不记录候选标题、下载地址或逐项匹配明细；
- 逐订阅开始、正常无结果、准入冲突，逐候选匹配/过滤，以及逐页站点进度降为 `DEBUG`；真实异常、媒体识别
  失败和下载业务结果仍保留原有错误或业务日志级别。

### 10.3 验证门禁

- 日志合同测试必须覆盖 Search/Match 开始与结束摘要、任务完成语义、准入冲突、取消、TTL、站点请求、错误冷却
  和两类释放失败；
- `100/10/1000` 与 `200/20/1200` 两档受控 Match 快照中，Match 模块的 `INFO` 数量固定为两条轮次摘要，
  不得随订阅数、站点数或候选乘积增长；
- 固定快照只验证日志量、字段和本地治理合同，不把它解释为真实 PT/TMDB/媒体服务器的长期网络 SLO。
