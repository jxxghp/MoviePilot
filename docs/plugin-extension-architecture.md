# 插件扩展架构设计

> 文档性质：设计决定与依据，不是使用说明
> 适用范围：插件如何向宿主注册身份、依赖与能力
> 相关：`docs/plugin-native-capability-poc.md`（一次已被否决方向的验证记录）

## 1. 问题

插件向宿主注册东西，一直混着三个本不相干的问题：

1. **我是谁、我需要谁** —— 身份与依赖
2. **我提供什么** —— 能力
3. **何时该启用我** —— 激活

三者被搅在一起，导致每加一种扩展点都得同时回答三个问题，于是出现了多条彼此重叠的注册车道：`get_module()` 的方法表、`get_channel_capabilities()`、`get_auth_providers()`、`get_agent_tools()`，各自独立演化。

本文把三者拆开，各自定归宿。

## 2. 三面分立

| 面 | 回答 | 载体 | 时机 | 强制性 |
|---|---|---|---|---|
| 身份与依赖 | 我是谁、我需要谁 | 插件仓库索引 `package.{version}.json` | **下载源码之前** | 有依赖才写 |
| 能力 | 我提供什么实现 | `provides_*` 钩子 | 加载后运行期 | 想提供才写 |
| 激活 | 何时该启用 | 用户开关（插件）/ 配置选择器（内建模块） | 运行期 | 无需声明 |

三个面全部可选。什么都不声明的插件行为与既有完全一致——这是对存量生态的硬约束，不是过渡期妥协。

### 2.1 为什么依赖必须放在仓库索引

依赖解析要回答「装 B 之前得先装什么、按什么顺序加载」。这个决策发生在**源码下载之前**，而插件源码目录里的任何文件最早只能在下载之后才可读。放在源码里，时机天然晚一拍：用户装 B、下载完、读到声明、才发现还缺 A，只能回头再装。

这也是所有包管理器的共同选择：依赖元数据必须可静态读取，且必须先于制品到达。

### 2.2 为什么能力不放索引，而走 `provides_*`

能力声明要能被校验。`provides_*` 在注册那一刻拿得到实现本身，可以确认类型是否符合、抽象方法是否落地、异步契约是否满足；不合契约的**拒绝注册**，而不是等到分发时才失败。

索引做不到这件事——它无法在不执行代码的前提下确认「声明的能力真的存在」。

索引里可以有**粗粒度能力标签**（见 §4），但那是给依赖匹配和市场检索用的广告，不是履约凭据。广告不实，履约时会被契约校验挡下。

### 2.3 为什么插件侧不设 per-plugin 能力清单

曾验证过一版「插件目录放 `capability.toml`、与内建模块共用能力注册表」的方案（记录见 `docs/plugin-native-capability-poc.md`）。机制可行，但方向被否决，理由是它两头不靠：

- 比索引晚：装完才可读，做不了依赖决策
- 比 `provides_*` 早：拿不到契约校验、类型校验、停用回收

它唯一不可替代的性质是免导入发现，而**该性质在进程内模型下兑现不了**——插件只要启用，宿主必然 import 它，声明面与实现面同时到场，先读清单一步没省。

附带代价是实打实的：双真相源会漂移；多版本并存时同一插件的多个版本声明同一个 id，注册表直接建不起来；清单本身成为新的故障面（实测「根里没有清单」「清单非法」「id 与内建重名」三种输入都会让宿主模块整体装载失败）。

内建模块保留 `capability.toml` 不受本条影响：内建模块多数未配置、多数带可选第三方依赖，「读到 `type=qbittorrent` 才 import 那一个」省的是启动时间，躲的是缺失可选依赖导致的 `ImportError`。这份收益内建侧拿得到，插件侧拿不到。

## 3. 进程内与进程外双形态

宿主有换实现语言的可能（`moviepilot-rust` 已是依赖），届时插件生态大概率以独立进程加客户端 SDK 的形式保留。本节的约束是为让声明面在那次切换中存活。

### 3.1 哪些能过去

三级分发原语映射得非常直接，因为它们本来就是**协议语义**而非实现细节：

| 原语 | 进程外对应 |
|---|---|
| 广播 broadcast | fan-out 通知，不等结果 |
| 多播 multicast | 并发 RPC，收集全部结果 |
| 单播 unicast | 依次询问，取首个认领者 |
| 管道 pipeline | 串行传递，逐段增强 |

让出协议同样成立：只有 `None`（及全 `None` 元组）算未认领，`[]`/`False`/`{}` 算已认领并短路——跨进程即「可空响应」，语义不变。

实例键 `plugin_id@instance_id` 天然映射成进程身份。仓库索引、依赖语义、废弃阶段表都是纯数据，与宿主语言无关。

### 3.2 哪些过不去

`provides_*` 若返回实现对象，则是纯进程内的东西：类对象无法跨进程传递；契约校验依赖语言内省（`issubclass`、抽象方法检查、协程判定），异语言宿主做不到；`_PluginBase` 继承与 `self.chain` 等进程内引用同理。

### 3.3 因此的设计规则

**`provides_*` 返回声明对象，不返回裸实现；实现作为声明的一个字段。**

```python
def provides_service_instances(self):
    """声明本插件提供的存储类型。"""
    return [ServiceInstanceDeclaration(
        capability="storage",                           # 数据，跨进程存活
        type="u115",                                    # 数据，跨进程存活
        name="115网盘",                                  # 数据，跨进程存活
        impl=U115Storage,                               # 进程内快路径，不过界
    )]
```

进程内时 `impl` 直接使用，契约校验照做；换成进程外时 `impl` 不参与序列化，其余字段原样成为握手报文，契约校验从「内省对象」退化为「校验 schema」——能力下降但不消失。

这是 Terraform provider 的既有形态：provider 是独立进程，握手时上报自身 schema，宿主按 schema 校验，本质是运行期传输的声明式数据。

该改造在当前几乎零成本，以后省一次全面重写。

### 3.4 声明数据只描述语义，不描述宿主的存储位置

同一条规则的另一面：跨得过去的必须是**协议语义**，因此声明字段不能拿宿主的内部坐标充当。

服务实例声明的第一个维度是 `capability`（`downloader`/`mediaserver`/`notification`/`storage`），不是这族配置在 systemconfig 里的列表名。前者是「我属于哪族服务」，跨进程握手时原样成立；后者是宿主当前把配置存在哪儿，换存储、换宿主语言即失效，而扩展本来就没有理由知道它。

模块声明归属服务族的 `service_capability` 取的是同一套标签，内建模块清单里的 `metadata.service_capability` 同样如此——三处声明一套词表。**清单不是插件面，但它与插件声明共用取值时，两套词表本身就是债**：同一族服务在一处叫 `downloader`、在另一处叫 `Downloaders`，任何跨两侧的校验、诊断与文档都得先做一次翻译。

标签到存储位置的对照收在宿主内部（`app/runtime/extensions/service_config.py`），是这套映射的唯一落点。存储位置只在真正读写 systemconfig 的地方出现：配置读取端口，以及内建清单的 `activation.watch` 与 selector——那两处描述的是「监听哪个键的变更」，本来就是存储位置而非语义。

### 3.5 构造方式是两条路径，不是一种形状

宿主构造服务实例有两条路径：`impl` 由宿主按 `impl(name=配置名, **配置内容)` 展开配置，`factory` 把整条配置对象交给扩展自行构造。二选一，同时给出或都不给出都拒绝登记。

只留 `impl` 等于要求扩展的类长成能被关键字展开的形状——那是宿主构造习惯外溢成插件的类型约束。`factory` 把这层约束换成一次函数调用，扩展想包装既有客户端、想按配置分派不同实现都不必改类。两条路径都是进程内快路径，跨进程时同样不参与序列化。

**存储族里这两个字段的读法不同，判据见 §7.5。**`impl` 在该族回答的是「按令牌取用的后端类是谁」，不是「怎么构造」；构造一律走工厂，`factory` 缺省时用宿主默认那一个。因此该族的 `factory` 是可选项而不是 `impl` 的替代项，二选一那条不适用。

### 3.6 一件事只由一条声明回答，不拆成两个各自合法的半条

媒体数据源原先要写两个钩子：`provides_media_sources()` 报展示信息，`provides_modules()` 挂识别与刮削的实现。两条声明各自独立合法，因此**只写一半也能通过契约校验**：只写实现的来源能被调用却进不了来源列表，用户在界面上选不到；只写展示信息的来源出现在列表里，选中后调用落空。两种残缺都要到用户使用时才暴露。

判据是**宿主能不能在登记时判定完整性**。能，声明就必须自足——`MediaSourceDeclaration` 因此携带 `methods`，与展示字段写在同一条里，缺任一半即拒绝登记。这不与 §3.3 冲突：`methods` 是「方法名到实现」的表，与 `ModuleDeclaration.methods` 同形，跨进程时同样退化为方法名清单，实现不过界。

合并另有一份净收益。多来源契约（`media_detail`、`discover`、`match_media` 等）由多个数据源共用一个分发名，靠调用方传入的 `source` 区分；非本来源必须返回 `None` 让出，返回 `[]` 会被判为已认领而短路，把该契约下的其余来源一并拦掉。这条协议原先只能写进文档指望实现方自觉，因为宿主拿到的是一张裸方法表，不知道表里的实现服务哪个来源。声明合并后宿主知道了，于是**让出由宿主按声明的 `media_source` 自动完成**：调用带的来源不匹配时实现根本不被触达。路由依据是纯声明数据，异语言宿主拿到同一份报文能做同样的事。

接管一个**已存在**的来源仍走 `provides_modules()`：那种写法没有新来源要进列表，宿主也无从预知它认领哪个 `source`，因此保留自认领语义，只在实例挂了多来源契约方法却未声明任何数据源时提示一次。这里不能改成拒绝——「接管已有来源」与「漏写数据源声明」在登记时长得一模一样，拒绝会把前者一并挡掉。

### 3.7 能力面从方法名推导，不新增声明字段

一张扁平的来源清单答不了「这个来源能拿来做什么」。只做发现的来源与做元数据识别的来源混在一起，用户在识别源里选中前者，调用按来源分发下去无人认领，**静默落空**——不报错、什么都不发生，看上去像网络问题。

不拆成两条声明。拆了会重新制造 §3.6 刚消灭的形态：同时占识别与发现两个面的来源得写两条声明且 `media_source` 是同一个值，作者写一半照样通过校验。取用形状也相同——都是「方法名 + 来源收窄」走同一套分发与弃权协议，按 §7.2 的判据形状相同不分族。

**能力面是 `methods` 键的函数**，宿主本就知道每条声明挂了哪些方法。让作者再声明一遍等于把同一件事写两处，写漏的那一处照样过校验。同理**不要求作者给不支持的方法补空桩**：空桩与不写在运行时等价，却提高误写 `return []` 的概率——按弃权协议 `[]` 算已认领并短路单播。

归入同一面的方法取用形状相同，收窄键不必相同：`match_media` 一族由宿主按 `source` 路由，`recognize_media`、`search_medias` 与刮削族由实现按 `media_source`/`scrape_source` 自认领，但对用户是同一个选择。按 `server`/`itemid` 收窄的 `media_exists` 问的是「哪台媒体服务器有」，与来源无关，因此不构成任何一个面。

| 面 | 契约方法 |
|---|---|
| 识别 `recognize` | `recognize_media`、`match_media` |
| 搜索 `search` | `search_medias` |
| 详情 `detail` | `media_detail`、`media_credits`、`person_detail`、`person_credits` |
| 推荐 `recommend` | `media_recommend`、`media_similar` |
| 发现 `discover` | `discover`、`discover_board` |
| 刮削 `scrape` | `obtain_images`、`metadata_nfo`、`metadata_img` |

`async_` 变体去前缀后与同名同步方法共用一份契约，归入同一面。列举顺序取自划分表本身，与方法登记先后无关（§7.2）。

推导只读取已有事实，**不改变任何分发行为**：一个方法在不在某个面里，不影响它被谁调用、何时短路。

内建来源是唯一的例外面。内建实现挂在模块类上而不是声明里，因此内建侧的展示名称、媒体类型与能力面记在 `app/api/endpoints/media.py` 的来源表上。表里不带能力面的来源在内建侧没有任何实现，实现由插件补上，能力面随插件声明推导后并入同一行。

**「模块与来源之间没有可供反查的绑定」这一条已经不成立**：模块在自己的 `capability.toml` 里用 `metadata.media_sources` 声明服务哪些来源，一个模块可以声明多个（`DoubanModule` 声明豆瓣与豆瓣音乐），一个来源至多由一个模块声明，重复声明在清单校验时即被拒。该声明目前的取用方是清单校验与来源表的一致性门禁——新增媒体来源模块却忘了往表里加行时会被挡下。

**能力面仍不能推导**，缺的不是绑定而是方法表的粒度：`DoubanModule` 一个类同时服务两个来源，两者能力面不同，而模块交出的是一张共用的方法表，宿主无从把表里的方法拆给两个来源。要让内建侧也走推导，得先让来源与方法表一一对应——要么把豆瓣音乐拆成独立模块，要么让清单逐来源列出方法名，而后者是把宿主已知的事实再写一遍，正是 §3.7 开头拒绝的形态。此外来源列表要在任何模块启动之前就能渲染，而能力索引是运行态的；那张表还是来源列表的唯一出口，改坏了整个来源选择一起失效。三条合起来，表继续留着。

## 4. 声明的配置界面

一个扩展可以同时声明多种能力，例如既提供存储后端又提供下载器。它们的配置分别属于
存储设置与下载器设置两个场景，而扩展只有一个 ``get_form()``，表达不了这种分派。

### 4.1 归属规则

**每份配置界面归属于声明它的那条声明，不归属扩展本身。**

| 界面 | 归属 | 渲染场景 |
|---|---|---|
| ``get_form()`` | 扩展自身 | 插件设置页 |
| ``ServiceInstanceDeclaration.config_form`` | 该服务类型 | 该服务配置族的设置页，例如下载器设置页、存储设置页 |

一个扩展声明 N 种能力即有 N+1 份界面，各自只在自己的场景出现，互不干扰，也不需要
扩展在单一表单里用条件分支拼装。

### 4.2 为什么内建类型不受影响

内建下载器与存储的配置模型是 ``type`` 加自由的 ``config`` 字典，界面按 ``type``
在前端渲染。内建类型的界面前端已内置，扩展引入的新 ``type`` 前端没有对应界面——
声明自带表单填的正是这个缺口，内建路径一行不改。

### 4.3 与跨进程形态的关系

表单是 Vuetify 组件树加默认数据，是纯数据结构，与 ``config_schema``、``trigger_args``
一样能序列化。因此它放在声明里不破坏 §3.3 的约束：跨进程时随声明原样成为握手
报文的一部分，只有 ``impl`` 不过界。

### 4.4 配置界面是呈现，配置契约是形状，两者并列不互相推导

声明能说「这个类型的配置界面长什么样」，此前说不出「这个类型的配置**是什么形状**」。
后果有四条：后端拿不到判据，前端交上来什么就存什么；新族无形可依，内建三族靠具型
配置模型兜底，插件将来声明的新族什么都没有；vue 模式下宿主连组件树都看不到，更谈不
上从界面反推形状；而 §3.3 要求声明能活过进程外宿主，一份只有 UI 树的声明过不去。

因此 ``ServiceInstanceDeclaration`` 另带 ``config_schema``。它**不**由 ``config_form``
生成，也不生成 ``config_form``：本分支明确支持 vue 模式，那种情况下表单是扩展自带的
联邦组件，从契约推不出来；反过来组件树里的校验规则也不是形状本身。分工是契约管后端
判定与跨进程握手，界面管呈现。

**取 JSON Schema 的一个受控子集**，判据是契约的消费方不止一个：宿主用它拒绝写入、
前端在没有 ``config_form`` 时用它生成默认表单、异语言宿主用它做同一件事。标准词表在
三侧都有现成实现，自定义字段描述结构要各写一遍；而它本身就是纯 JSON，§3.3 的可序列化
要求不需要额外机制来满足——契约校验按「JSON 往返后是否与原值相等」判定，元组、集合、
非字符串键这类只在进程内成立的形状当场被拒。

**取子集而不是全集**，是因为宿主必须真的能判定。``$ref``/``allOf``/``if`` 这类关键字
若被悄悄忽略，得到的是一份看起来有效、实际拦不住任何东西的契约，比没有契约更坏。因此
关键字集合是封闭的：子集之外的关键字一律判整条声明不合契约，宿主永远不会面对自己评估
不了的构造。

**契约描述的是类型自己的配置内容**，即该族配置模型 ``config`` 字段的形状，不描述
``name``/``type``/``enabled``/``path_mapping`` 这类外壳字段——外壳属于服务族，是宿主
的东西，类型没有理由描述它，这也是 §3.4 的同一条规则。走 ``impl`` 路径时契约还不得声明
名为 ``name`` 的字段：实例名由宿主按 ``impl(name=配置名, **配置内容)`` 填入，同名会让
构造得到两个 ``name``；``factory`` 路径没有这次填入，因此该保留字只在 ``impl`` 路径成立。

判定挂在两处：**配置写入路径**（``POST /system/setting/{key}`` 与智能体的系统设置工具）
在配置落盘前退回并说明是哪个实例的哪个字段有问题；**实例构造路径**
（``create_service_instance``）再判一次，因为配置也可能从别的入口进来——旧版本存下的
数据、直接改库、宿主自己的迁移都不经过写入端点。两处共用同一个判定函数，因此不会出现
「写得进去、用不起来」的分歧。构造路径的判定按既有的逐条错误隔离处理：一条坏配置只影响
它自己。

**契约当前可选、未声明即退化为原行为**，走向必填的路径挂在 §6 的三阶段废弃框架上：
``plugin.service_instance_without_config_schema`` 现处 WARN，声明未带契约时按声明方
提示一次，功能照常；推进到 DISABLED 后同一处判据即把未带契约的声明判为违约，调用点
一行不改。内建三族当前不声明契约，走具型配置模型这条老路，因此它们落在同一条退化分叉上。

## 5. 依赖语义

索引中区分两种依赖，语义不同：

```json
{
  "id": "U115Helper",
  "requires": ["storage:u115"],
  "depends": ["U115StoragePlugin"]
}
```

- **`requires`（依赖能力）** —— 任何提供该能力的实现都满足。同一能力多实现是常态而非例外：`recognize_media` 有 themoviedb、douban、bangumi、anilist、musicbrainz，`list_files` 有 u115、alipan、alist、rclone、smb、localstorage。若 115 接入同时存在 open API 与网页协议两种实现，助手类插件不应被绑死在其中一种上。
- **`depends`（依赖具体插件）** —— 用于消费对方私有面：直接导入其类、读其数据表、调其自定义方法。这类依赖不是能力契约能覆盖的。

### 5.1 对 `depends` 的立场

私有面依赖在进程外模型下代价极高：跨进程消费私有面，要求对方为「私有」的东西开 RPC，与私有的定义矛盾。

因此 `depends` 予以支持但不鼓励，并作为渐进式废弃框架的登记候选，在文档与告警中标明它是进程内特权、未来可能受限。新插件应优先用 `requires`。

### 5.2 待定项

以下问题需在实现前定案，本文不预设答案：

1. 停用或卸载被依赖方时依赖方如何处置——级联停用，还是拒绝操作并提示仍被依赖（倾向后者，更符合直觉，但需要反向依赖索引）
2. 版本约束的表达与匹配，及其与多版本绑定机制的交汇
3. 安装依赖方时是否自动拉取被依赖方
4. 能力标签词表（`storage:u115` 这类标识）的命名约定与登记方式

## 6. 迁移

`app/runtime/deprecation` 提供三阶段退场，推进只改登记表里的 `stage`，调用点不动：

```
WARN      功能照常，首次触达告警一次（按标识与来源去重）
  ↓
DISABLED  默认关闭，标识列入 DEPRECATION_ENABLED 可临时恢复——用于观察真实依赖方
  ↓
REMOVED   触达即报错并给出迁移指引
```

首批登记含 `plugin.get_module`（当前 WARN），废弃理由是「按方法名劫持内建模块实现，无契约校验、无归属记账、卸载不可回收」，替代方案为 `provides_*`。

**未在索引中声明任何东西的插件不进入任何废弃流程**——它们不在被废弃的范围内。被废弃的是具体的旧写法，不是「没有声明」这件事本身。

## 7. 已裁决：两种「扇出」不并轨，边界写在这里

宿主里有两处都被叫作「扇出」的东西：**扩展分身**按 `plugin_id@instance_id` 展开多个
行为体，**服务实例**按用户配置列表展开多个具名实例。此前记在册的判断是「两者结构同形、
是同一件事的两套实现，待并轨」。逐条比对后**这个判断不成立，本节改记裁决结果：不并轨**。

### 7.1 逐条比对与裁决

|  | 扩展分身 | 服务实例 |
|---|---|---|
| 身份键 | `plugin_id@instance_id`，宿主运行态标识 | 配置里的 `name`，用户自填、出现在业务数据里 |
| 配置来源 | `PluginConfig` 表，每分身一行 | systemconfig 里的一个列表，每类型 N 条 |
| 谁扇出 | `PluginManager.start()` | `ServiceBase.init_service()` 与 `ServiceInstanceAdapter` |
| 触发时机 | 用户显式建分身、装载插件、切版本 | 模块初始化与每次取服务，按当时的配置内容推导 |
| 回收时机 | 停止实例、停用插件、删分身 | 配置条目消失即摘除，无独立回收动作 |
| 分身自有 | 数据目录、自有库、事件处理器注册、调度任务、版本绑定 | 无，实例只是一条配置的活的投影 |
| 错误处理 | 单分身构造失败只跳过它自己，兄弟分身照常运行 | 单条配置构造失败只跳过它自己，同类型其余实例照常产出 |

**裁决：不并轨。** 两者回答的不是同一个问题。分身回答「同一份代码要跑几套行为」，服务实例
回答「同一个接入类型要连几个外部对象」。判据是**实例消失时用户损失了什么**：分身消失，它
自己的库、数据目录、调度任务与版本绑定一并消失，因此它必须有显式的建与删；服务实例消失就
只是一条配置不再生效，重新填回配置即完全恢复，因此它不需要也不应该有独立生命周期。强行
并轨的两个方向都要付代价——把服务实例做成分身，等于给每台 qBittorrent 配一行 `PluginConfig`、
一个数据目录和一份版本绑定，全是无意义的账；把分身做成服务实例，等于让分身丢掉自有库与
版本绑定，那正是分身机制存在的理由。

这条裁决与 §7.3、§7.4 是同一套判断的三个侧面：§7.3 判定服务实例**类型**声明是扩展级、
不随分身扇出，§7.4 判定 `multi_instance` 与「扩展本体是否分身」正交。三者若不一致，本节
并轨就会让 §7.3 自相矛盾。**两者刻意相邻而不重合，这是设计，不是欠账。**

### 7.1.1 真正的重复在另一处，已消除

原记录说「重复的是扇出机制」，查证后**重复不在两种扇出之间**——两侧除了都有一个 for 循环，
没有一行可共用的代码：配置来源、身份键、失败语义、回收时机全都不同，抽公共抽象只会得到
一层假 DRY。

真正的重复在**服务实例这一侧自己有两份实现**：内建三族走 `ServiceBase.init_service()`，
扩展声明的类型走 `ServiceInstanceAdapter`，两份各自实现了同一件事，并且已经跑偏：

- **筛配置**：「按类型标识、启用态筛出该类型的配置并按实例名建表」在三个内建族基类里各抄
  一遍、在适配器里再抄一遍，共四份。内建那三份不检查配置有没有名字，会产出一个键为空的
  实例——它既无法被显式指定，也无法被默认配置裁决选中。
- **构造实例**：`impl(name=..., **配置内容)` 与 `factory(配置对象)` 这两条路径两侧各写一遍。
  扩展侧逐条隔离失败，内建侧没有：**一条连不上的用户配置会让整个内建模块初始化失败，连带
  该类型下其余可用实例全部消失**，惩罚范围远超问题本身，也与扩展侧的行为不一致。

两份已收敛为一份，落在 `app/runtime/extensions/service_config.py` 的 `select_instance_configs`
与 `create_service_instance`，两侧共用。收敛后内建侧获得逐条错误隔离与具名校验，扩展侧行为
不变。构造形状因此与 `service_instance_capabilities` 的契约校验对着同一份实现：校验过的形状
就是实际构造用的形状。

**服务族基类不再逐族实现 `get_configs()`**，改为在基类上按 `SERVICE_CAPABILITY` 一次实现；
族之间的差别只剩能力标签这一个类属性。

### 7.1.2 没并轨、也不打算并的部分

服务实例带宿主级**选择语义**——哪个是默认下载器、路径怎么映射、下载任务派给谁；分身之间
没有这种选择。§7.2 已分别裁决两侧「调用未指定目标时怎么办」，两套规则不同且都成立，不必
统一到一处。

再出现同类需求时的判据是 §7.3 末尾那条：**改变的是行为就用分身，改变的是接入对象就提供
服务类型。** 不要实现第三套扇出。

### 7.2 三处隐式回落的裁决

调用未指定实例时的裁决规则是：有显式默认则用，无默认或默认已停用则报错，**不取第一个、
不取任意一个**。宿主内三处旧回落按下述口径对齐，报错一律列出候选并标注启用态。

**下载器默认配置解析**（`_DownloaderBase.get_default_config_name`）。原实现扫全部下载器取首个，
既不看启用态也不看类型，会让某类型的模块返回并缓存一个它根本不持有的名字。现在：默认标记
已启用且属于本类型才认领；属于别的类型返回空，安静让该类型的模块接手；标记已停用一律报错，
不改走另一个下载器。从未标记过默认时，只在全部已启用下载器恰好一条的前提下认定它就是目标。
报错只由持有已启用配置的模块发出，没有候选的模块保持沉默，避免三个下载器模块重复告警。

**媒体服务器与通知的默认配置解析**（`ServiceBase.get_default_config_name`）。选择保留回落但
收窄到「本模块名下恰好一条已启用配置」，多于一条报错。判据是：新规则要禁的是在多个候选里
替用户做选择，而候选唯一时结果与登记顺序无关，不构成选择；「取第一条」的危害恰恰来自它依赖
顺序。

这两族的默认标记字段已经有了——`serviceconfig` 表的 `is_default_target` 对每一族都成立，读出来
即三族配置模型顶层的 `default`——但**配置界面还没有指定它的入口**，此刻一律读到假值。因此回落
暂时留着：先按「唯一即回落」跑，等界面能写这个字段，再把这两族一并切到与下载器相同的裁决。
单实例类型的裁决（§7.4）不受此限，它本来就只在配了多份时才需要目标，没有默认就报错。

**运行实例解析**。原判据「传扩展标识且恰好只有一个实例在跑即命中该实例」删除。边界划在
**查表与选目标是两件事**：运行态表只回答「这个键指的实体在不在」，按实例键精确命中；「调用没
指定实例时该走哪一个」全部交给默认调用目标裁决。与前两族不同，插件实例已经有显式的默认调用
目标字段与写入口，「只建了分身、没有默认」是用户可以且应当消除的状态，因此这里不需要「唯一
即回落」这个补偿，直接按规则报错并提示去指定。

调用方按用途分流：读插件名、版本这类类级属性取任一运行实例即可，不构成调用目标选择；按插件
标识调用实例方法则走裁决，裁决不出来时抛错而不是返回空。

### 7.3 声明面按标识分两级：扩展级与分身级

§7 的两套扇出机制在声明面交汇：一个扩展建了 N 个分身，每个分身都会被问一遍「你提供什么」。
于是同一个标识可能被同一个扩展的多个分身各声明一次，而这件事有没有正当语义**取决于该族
声明的是什么**。

判据是**宿主拿到声明后用它做什么**：

- **扩展级** —— 声明登记的是「本宿主提供这个标识」这件进程级事实。宿主按标识全局建表、
  按标识构造，构造时不带声明方的实例配置。同一标识被同扩展多个分身各声明一次，得到的是
  同一件东西的 N 份副本，没有任何正当语义。
- **分身级** —— 声明携带的实现绑在声明它的那个分身上（绑定方法、按实例键寻址的入口），
  两个分身各声明一次即两个各自成立的行为体。这正是分身机制本身要表达的东西。

| 族 | 级别 | 依据 |
|---|---|---|
| 服务实例类型 `provides_service_instances`（含存储类型） | 扩展级 | 用户接多台同型号服务时配的是该类型自己的配置列表，不是多个分身；存储标识同理按标识全局登记 |
| 媒体数据源标识 `provides_media_sources` | 扩展级 | 来源标识是用户在界面上选的那一项，一个标识只该有一份展示信息与一份实现 |
| 智能体工具名 `provides_agent_tools` | 扩展级 | 工具类由智能体工厂自行构造，不接触声明方实例；重名会被工具目录判为身份歧义而拒绝解析 |
| 工作流动作 `provides_actions` | 分身级 | `impl` 通常是分身的绑定方法，同一 `action_id` 在两个分身上做的是两件事 |
| 名称解析器 `provides_meta_parsers` | 分身级 | 解析环绑在声明它的分身上，两个分身各配一份模型即两个各自成立的环 |
| 仪表盘 `provides_dashboards` | 分身级 | 取用走 `(实例键, key)`，每个分身各有一块是正当配置 |
| 定时任务 `provides_schedules` | 分身级 | 任务 id 由宿主拼成 `实例键_任务标识`，回调按实例键包装后日志落到该分身；两个分身各配一份 cron 即两份各自成立的调度 |
| 模块方法表 `provides_modules` | 分身级 | 方法表挂的是分身的绑定方法，聚合键取 `(实例键, 展示名)`；同一方法名在两个分身上是两套各自成立的实现 |
| 渠道能力 `provides_channel_capabilities` | 分身级 | 登记与撤销由每个分身自己的生命周期驱动、归属记到实例键；分身之间不去重，同一渠道标识的多方登记按跨扩展的覆盖规则裁决 |
| 登录入口类型 `provides_service_instances`（`capability="auth"`） | 扩展级 | 与其余服务实例类型同条，判据见 §7.8 |
| 登录入口旧钩子 `get_auth_providers` | 分身级 | 该钩子本身就是分身级写法，废弃期内维持原语义不变 |
| 筛选规则标识 `provides_filter_rules`、规则组名 `provides_filter_rule_groups` | 扩展级 | 标识进的是全局规则集与全局规则组表，按标识建表、按标识取用，声明本身也不携带实现 |
| 命令词 `provides_commands` | 扩展级 | 命令词进的是按命令词建键的全局命令表，也是外部渠道菜单里的命令名；用户手打它时不带任何实例限定符，宿主无从把同一个词分派给第二个分身 |

扩展级的族**按扩展标识去重，不按实例键**。认哪一个必须与分身的启动顺序无关，否则同一份
配置在两次启动后可能得到不同归属：规则是**默认实例优先，其余按实例标识升序取第一个**，
只读实例键本身，因此任何登记顺序都得到同一个结果。裁决收在
`app/runtime/extensions/admission/extension_scoped.py`，四族共用一份实现与一条告警文案。

**登记归属仍记到具体实例键**，回收按实例键精确进行；去重只决定「同一个标识被登记几次」，
不改变回收语义。胜出的分身停止或停用后，仍在运行且声明同一标识的兄弟分身重新参与裁决并
接手——该标识描述的是「本宿主提供它」，而宿主里还有分身提供它；全部分身停止后没有分身
可裁决，登记在各自的撤销里已经清干净。

去重只发生在**同一扩展的分身之间**。不同扩展声明同一标识按哪条规则处置，取决于**标识本身
是否承载了「意图替换」**，与本节无关：

- **标识指称同一个外部对象**时是后登记覆盖、停用即恢复被覆盖方。服务实例类型、存储标识与
  渠道能力的渠道标识属此：`u115` 就是 115 网盘，声明它即「我来提供这个后端的另一份实现」，
  声明标识本身就是覆盖意图。恢复靠的是**保留被压住的那一份**而不是重新查询：覆盖方停用时
  被覆盖方未必还会被问一遍，丢掉即等于该标识凭空消失。存储族的落点是内建登记快照
  （`storage_registry.py`），渠道能力族的落点是按渠道标识排队的登记列表
  （`app/schemas/notification.py` 的 `ChannelCapabilityManager`），两者都在撤销时做归属
  校验：被更晚的登记接管后，原登记方停自己那一份不会连带把接管方踢掉。
  渠道能力族另有一条不受本裁决影响的取用规则——**内建渠道优先**，扩展登记只在内建静态表
  未命中时才被查到，因此插件之间的覆盖裁决碰不到内建渠道。
- **标识不指称任何共同对象**时双方一并失效并告警一次。筛选规则标识、规则组名与命令词属此：
  `/sync` 在一个插件里是同步媒体库、在另一个插件里是同步网盘，没有哪一方算意图覆盖，宿主
  无从裁决谁对；按登记顺序取其一会让同一个词的行为随插件加载顺序变化，违反 §7.2。

**插件与内建同命令词**落在两者之间，因此裁决是「接管意图须显式声明」：声明
`overrides_builtin=True` 即按接管处置，插件命令生效、内建命令被压住；没声明就是撞车，该条
插件命令作废、内建命令保持生效并告警一次。内建命令词是宿主自己发布的稳定标识，用插件增强
`/subscribes` 是正当诉求，说「没有哪一方算意图覆盖」不成立；但命令词自己带不出「我要替换
内建行为」这个意思，接管与撞车从命令词分辨不出来，就把意图单列一个字段说出来。连内建一起
废会让任意插件随手起的命令词打掉宿主的 `/restart`，冲突不再落回安全态；一律内建胜出则堵死
正当诉求且是静默丢弃。裁决收在 `app/runtime/extensions/admission/command_arbitration.py`。

两类失效此前只在服务端日志里留过一次告警，用户敲了没反应无从得知原因。可见性入口：筛选规则
是 `GET /api/v1/filterrule/rules`，命令是 `GET /api/v1/command/origins` 与
`/api/v1/command/conflicts`。

**扩展作者该用分身还是该提供类型**，判据是配置改变的是什么：改变的是**行为**（这次处理哪些
事件、按哪套规则跑）就是分身；改变的是**接入对象**（连哪台服务器、用哪个账号）就是提供类型、
由用户在该类型的配置里加条目。今天宿主对这个选择**没有任何事前提示**——只有事后一次告警，
即上面那条「同一标识只登记一次」。事前提示需要扩展在索引里就自报它属于哪一类，那与 §4 的
粗粒度能力标签是同一件事，尚未定案。

### 7.4 一个类型能配几份由声明表达，不由族硬编码

宿主原先按服务族推定实例数：下载器、媒体服务器、通知一律多实例，储存器一律单实例。这个
划分实测不成立——储存器用户确实要配多份（多个网盘、多个 rclone remote），而认证器**同族内
两种都有**：第三方站点单点登录全局只有一份配置，媒体服务器单点登录要每台一份。族是「这类
服务长什么样」，配几份是「这个具体类型怎么用」，把后者绑在前者上，只要有一个反例整族就得
开特例。

因此实例数是 `ServiceInstanceDeclaration.multi_instance`，由声明该类型的一方回答，缺省为
多实例。缺省值让既有三族行为不变：它们本来就是多实例，不写该字段即维持原状。认证并族后
那个反例兑现成了字段：同一族里第三方站点单点登录声明 `multi_instance=False`，媒体服务器
单点登录声明 `True`（见 §7.8）。

**内建类型声明在各自的 `capability.toml` 里**，键是 `metadata.service_instance`，同一个
字段名、同一套缺省。内建类型不进类型目录（§7.5），因此它答不上「能配几份」时前端只能按
缺省渲染出新增第二份的入口——本地存储只有一个文件系统、第二份配置指的仍是同一个盘，那个
入口是错的，而它正是「族推定不成立」的又一个反例。声明落在清单而不是后端类的类属性上，
是因为前端渲染配置列表时后端类还没被导入：清单是磁盘上的数据，模块起没起来都读得到。

**该字段与「扩展本体是否分身」正交**，两者回答的不是同一个问题：分身是扩展按
`plugin_id@instance_id` 扇出的多个行为体，各自独立运行、各自持有配置；`multi_instance`
描述的是该类型的配置列表允许有几条记录。只建了默认分身的扩展照样能提供多实例类型，建了
多个分身的扩展提供的类型也可以只认一份配置。§7 记的两套扇出机制在此处再次相邻但不重合。

**单实例类型被配了多份时按默认调用目标裁决，裁决不出来就整类型停摆并报错。** 规则与 §7.2
完全一致：有显式默认则用，无默认或默认已停用则报错并列出候选，不取第一个。

这条曾经是「只认列表里排在最前的一份并告警一次」，理由是配置列表属于用户自己排的持久数据，
顺序在设置页上可见、每次读取都一致，因此「第一条生效」是用户看得见也改得动的规则。实例配置
搬进 `serviceconfig` 表后这个前提没有了——表里没有顺序列，「第一条」退化成主键先后，正是
§7.2 禁掉的那类挑选。前提消失，结论跟着改，两处于是收敛到同一条裁决规则。

多出来的配置仍然只忽略不删除：声明改成单实例前用户可能已经配了多份，删配置不可逆。代价是
裁决不出目标时该类型一个实例都不产出——但这比替用户挑一份跑起来轻：挑错的那份可能正连着
另一台服务器，而停摆至少是可见的、报错里带着候选和改法。

### 7.5 存储并入服务实例族：配置面与声明面都合并

存储的实例配置此前自成一路：自己的整形函数、自己的默认裁决、`read_system_setting` 里
自己的一条分支。逐条比对后，配置面上它与三族一模一样——用户在一份配置列表里配 N 条，
宿主扇出 N 个具名实例，一条坏配置只影响它自己。因此**配置面合并**：`storage` 进服务族
登记表与族落点表，与三族同一张 `serviceconfig`、同一套整形（分列、身份归一、默认标记
裁剪）、同一份 `select_instance_configs` 筛选与单实例裁决。`app/application/storage_config.py`
只剩存储自己的两件事：把原始条目解析成配置对象，以及按令牌选出目标实例。

**声明面也合并。** 曾经的判断是「字段是子集，协议不是」——三族的实例由宿主把配置内容
展开进构造参数（`impl(name=配置名, **配置内容)`），或整条配置交给 `factory`；存储后端两条
都不是，它按实例归属构造（`后端类(storage_instance=实例名)`），配置由后端自己按存储令牌
懒读，因为存储配置要支持运行期改写后重连。**那条论证只盯着 `impl` 路径。**`factory(conf)`
拿到的是整条配置对象，只取 `conf.name` 去构造 `后端类(storage_instance=conf.name)` 完全
成立，一个配置字段都不必往构造函数里传。协议是够用的。

真正的顾虑是下一句：这样要求每个扩展作者手写一个工厂，把宿主本来就会做的归属交付重做
一遍。**那是人体工学问题，不是协议问题**，而人体工学问题由宿主出默认实现解决：

- 声明只给 `impl`（存储后端类）时，宿主用默认工厂
  `storage_instance_factory`——就是内建存储那套「`StorageBackendMeta` 在 `__init__`
  之前交付归属、`StorageInstanceSingleton` 按 `(类, 实例名)` 复用」，扩展作者一行工厂都
  不用写。
- 声明给了 `factory` 就走它，宿主只交出整条配置对象。

因此 `provides_storages()` 与 `StorageDeclaration` **删除**，不保留为语法糖。判据是「保留
它会不会造成两条并行的登记路径」：保留就要保留第二条投影、第二个契约校验、第二个登记
函数与第二次回收，而两条路径同时存在正是要消除的东西；它只存在于本重构线、从未随任何
发行版到达社区，删除不会让已发布插件失效。

合并留下的**唯一一处族分支**在构造路径的读法上，写在契约校验与登记两处：存储族里 `impl`
回答「按令牌取用的后端类是谁」而不是「怎么构造」，因此它必填、按继承判定契约、不做
`impl(name=...)` 的签名内省；`factory` 是可选项而不是 `impl` 的替代项，§3.5 的二选一
在该族不适用。这处分支是有意留的：它把作者侧的样板换成了宿主侧的十来行。

**两张登记表都留着，不是副本。** 存储类型登记两处：

| 表 | 键 | 回答的问题 |
|---|---|---|
| `storage_backend_registry` | `(存储标识, 实例名)` | `u115@work` 这个令牌指的实体是谁 |
| `service_instance_registry` | `(能力标签, 类型标识)` | 这个类型谁提供、能配几份、配置什么形状、界面长什么样 |

粒度不同，方向也不同：前者按实例寻址、要能内省后端类有没有某个方法，后者按类型记账、
不持有任何实例。类型目录推不出按实例寻址，后端注册表也答不出 `provider` 与
`config_schema`。此外内建存储的类型来自各自的 `capability.toml` 而不进类型目录，与三族
的内建类型口径一致，两表的行集合本就不同。因此写入端契约判定、`provider` 记账与类型信息
端点对插件存储类型自动生效，而整理编排仍按令牌直取后端。代价是两处登记的回收必须在同一次
同步里做完，否则后跑的一方按登记方回收时会把先跑的一方刚建好的登记扫掉——并族后这已经是
同一个函数里的同一轮循环。

### 7.6 默认调用目标每族一个，裸令牌兼容指针不是默认

并族后存储的 `is_default_target` **启用**，与三族完全同规格：每族至多一个，落
`serviceconfig` 专列，唯一性由条件唯一索引 `(capability) WHERE is_default_target` 判定，
单实例类型的裁决读的也是它。这补上了一个此前缺失的能力——存储的该列曾经恒为假，
「用户没指定存储时用哪个」根本无解。

曾经的记录把这一格填成「存储的默认是每个类型一个」，理由是存储的调用地址 `u115:/media`
已经写死了类型、只缺实例段。**观察没错，结论错了**：那是把**地址兼容**当成了**默认机制**。
两件事拆开：

| | 是什么 | 粒度 | 落点 |
|---|---|---|---|
| `is_default_target` | 用户没指定存储时用哪个 | 每族一个，与三族一致 | `serviceconfig.is_default_target` 专列 |
| 裸令牌兼容指针 `bare_token_target` | 存量路径 `u115:` 指向该类型的哪个实例 | 每类型一个 | 族配置模型的实例级字段，随 `host_config` 落库 |

兼容指针**不叫默认**，因为它不做选择：令牌已经把类型定死了，它只补地址里空着的实例段。
它是存量路径没有实例名才需要的兼容层，**退场路径**是把所有路径补全实例名
（`u115@主号:/media`）——补完之后 `select_storage_config` 的无实例名分支、
`_trim_bare_token_pointers` 与该字段一并删除，取不到实例名的令牌直接判为不合法，
默认调用目标不受影响。

两者**语义不重叠**：族级默认回答「没指定存储」，兼容指针回答「指定了类型没指定实例」。
一个存储实例可以同时是族级默认与它那个类型的兼容指针，也可以只是其中之一。互不干扰是
结构性的，不靠约定：两者各占各的载体，族级那个是外壳字段 `default`、映射到专列，兼容指针
是宿主载荷里的实例级字段，条件唯一索引一行都不占。

兼容指针裁的是**恰好一条**而不是至多一条：裸令牌必须始终指得到实例，一份都不标记会让该
类型已有的裸路径整体失效。裸令牌的裁决因此仍是那条老规则——未具名配置占据裸令牌位，优先
命中；全为具名时只认唯一一个自称承接的；无人自称或多份自称一律**让出**，绝不取第一个。

### 7.7 管道型扩展点的顺序是用户数据，不是登记顺序

名称解析是宿主里第一个「顺序即语义」的扩展点：各环串成管道，谁先跑决定谁的结果
会被下游覆盖。因此它不能沿用其它族「按扩展 priority 排序」的做法——那是宿主内部
的登记面，用户既看不见也无法预期，正是 §7.2 禁掉的那类挑选。

执行顺序落在 systemconfig 的 `MetaParserOrder`：一条条 `(解析器标识, 是否启用)`，
与规则组同属用户自己排的持久数据，顺序在设置页上可见、每次读取都一致，还能单独
关掉某一环。声明里的 `priority` 只决定一个解析器**初次出现**时排在哪，用户排过之后
它不再参与。

管道的控制权在宿主：每一环拿到当前累积结果、交回自己的贡献，宿主负责合并。扩展
拿不到 `next()`，因此一环失败只跳过这一环，链条继续，内建环恒不弃权。给出
`next()` 等于让任一扩展能左右宿主全局行为——`init_service` 曾因一条坏配置让整个
内建模块起不来，那个失败模式不再复制一份。

下游环可以改写上游已填的字段，不限于补空位：内建解错时是自信地填了错值而不是留空，
只补空救不了这类错误。代价一并付清——宿主为每个字段记录来源与被覆盖前的取值
（`MetaParseTrace`），「为什么识别成这个」因此有答案，覆盖也不是暗箱操作。

### 7.8 登录入口并入服务实例族：身份标识不动，默认目标不设

登录入口原先是**分身级**的：一个分身一个入口，用户要把第二台 Emby 也做成登录入口，
得去建一个插件分身。按 §7.3 末尾那条判据复核，这个划法不成立——改变的是**接入对象**
（连哪台服务器、用哪个账号）而不是行为，正该由该类型自己的配置列表承载。份数差异恰好
落在 §7.4 的 `multi_instance` 上：第三方站点单点登录「一种类型一份配置」，媒体服务器
单点登录「每台一份」。

因此 `auth` 进服务族登记表与族落点表，与其余各族同一张 `serviceconfig`、同一套整形、
同一份 `select_instance_configs` 筛选与单实例裁决；`provides_auth_providers()` 与
`AuthProviderDeclaration` **删除**，登录入口类型改由 `provides_service_instances()`
声明。判据与存储那次同：保留薄封装省不掉第二条投影、第二个契约入口、第二个登记函数与
第二次回收。该钩子只存在于本重构线，从未随发行版到达社区，删除不使已发布插件失效，
因此也不进废弃表——废弃表是给插件作者看的对外契约。**分身级旧钩子 `get_auth_providers()`
不同**，它随 v2 发行版到达过社区、已在废弃表里，因此照常走三阶段退场，替代方案改指
本节的声明写法。

**入口标识不改口径，因为宿主从来不拥有它。** 身份绑定表的 `provider` 列是
`UNIQUE(provider, external_id)` 的一半，失效就是丢绑定——这与存储那次完全不同，那里
`provider` 失效只影响提示文案。查证结论是：该列的取值一直由插件在签发登录票据时
（`create_plugin_auth_ticket_for_identity`）原样交来，宿主既不生成也不校验；并族改的是
入口的配置载体与扇出方式，没有触及这一列。**存量绑定因此零迁移。**

反过来说，**靠迁移脚本改写存量取值是做不到的**，两头都推不出来：旧值是插件自选的任意
字符串（常见是宿主回落值 `plugin:<实例键>`，但插件也可以填 `oidc` 这类自定义标识），而
新入口的类型与实例名在升级那一刻根本不存在——并族前登录入口不是配置，`serviceconfig` 里
一条 `auth` 行都没有，用户要先去配才有。没有映射可写，也没有行可搬。

存量入口的承接由**入口配置的一个实例级宿主字段** `identity_provider` 完成：它就是本入口
写进 `provider` 列的取值，用户不填时宿主按 `类型@实例名` 派生，填了就用填的那个。要接住
分身时代的绑定，把它填成旧取值即可，绑定表一行不动。同一个字段也兜住派生取值的另一面：
派生值随实例名走，改名即换入口，先把改名前的取值填进该字段再改名就不丢绑定。同一件事的另一面是身份歧义：两条
配置落到同一个取值，**两条都不产出入口**，不做裁决——挑一条胜出等于把另一台服务器的账号
静默并进胜出者的身份命名空间，用户看到的就是「登进了别人的账号」；剔除至少是可见的，
入口从登录页消失、日志里带着冲突方与改法。

**该族不设默认调用目标。** 族级默认回答的是「调用没指定用哪个」，而登录时用户点的永远
是具体某个按钮，不存在未指定这回事。语义不符还占着 `is_default_target`，代价是实打实的：
那一列由条件唯一索引 `(capability) WHERE is_default_target` 把关，用户给第二条入口配置
置位时会撞索引，整次写入连带失败。因此族落点规则上标出该族没有默认目标，写入整形一律把
它裁成假，`auth` 在那条索引里永远不占位。连带的后果是单实例类型被配多份时裁决恒定无解，
按 §7.4 的既定口径整类型停摆并报错列候选——这正是「绝不替用户挑一份」的结果。

**登录入口列表不经实例构造。** 登录页在任何用户会话之前渲染，是所有登录方式的唯一入口；
一次实例构造失败若能让整族入口消失，用户就再也进不来。因此入口列表只取「该族配置 + 类型
登记」这两样纯数据（`app/runtime/extensions/projection/auth_entries.py`），构造留给真正要完成认证
握手的那条路径。这与 §7.5 那两张登记表是同一种分工：一张回答「这条配置活成什么对象」，
一张回答「登录页该显示什么」。配置读取端口在未登录状态下照常可用（它是一次普通的表读取），
而入口描述只带展示与路由字段、不带 `config` 载荷——登录入口的配置里装着客户端密钥。

隔离粒度有两层：单个类型裁决失败或读取出错只让该类型的入口消失，同族其余类型照常产出；
单条配置身份不成立只影响它自己。整族配置读取整体出错时退化为空列表，系统内建的通行密钥
入口不受影响。

### 7.9 扩展点作用于哪台服务实例，由声明表达

§7.3 划的是「声明挂在扩展还是挂在分身」，回答不了另一根轴：一个纯扩展型插件只建了一个
分身，用户配了多份的却是它提供的**服务实例**——三台下载器就是三台。动作要作用于其中一台、
仪表盘要展示其中一台的数据时，分身标识指不到它们。

原先插件只能自己在 `config_form` 里放一个「选哪台」的字段，代价是宿主完全不参与：用户填个
不存在的实例名要到运行时才炸；删掉一台下载器配置，引用它的仪表盘没有任何提示，与 §7.6
「提供方已消失」那条筛除能力接不上；每个作者各写各的选择器，同一件事在不同插件里长得不一样。

`ActionDeclaration` 与 `DashboardDeclaration` 因此各加一个**可选**字段
`requires_service_instance`，载体是 `ServiceInstanceRequirement`。四处裁决：

**一、形状是「能力标签 + 可选的类型收窄」，不含实例名。** 判据是宿主拿这份声明做什么——按
`capability` 找到该族配置列表当选择器数据源、按 `types` 收窄候选、在选中的实例消失时按同一
对坐标说清是哪一族的哪个实例不在了，三件事都不需要实例名。而实例名是用户在设置页自填的
持久数据，声明期根本不存在：插件被加载时用户可能一台下载器都还没配。声明随插件版本静态
发布、实例名随用户增删漂移，把后者钉进前者只会得到一个一改配置就失效、作者还无从修正的
引用。`types` 有实际指称——提供了某种下载器类型的插件，它的动作多半只对自家那种类型成立，
不收窄就会把别家类型的实例也列进选择器，选中后仍是运行时才炸。

**二、声明期只判形状，不判该族有没有登记。** 判据在校验的时机：`provided_actions()` 与
`provided_dashboards()` 不是装载期跑一次，而是每次投影都重跑。把「族已登记」写进声明是否
合规的判定，同一条声明就会因为提问时刻不同而一会儿合规一会儿不合规——某个带进新族的扩展
晚一步登记，先前那条拒绝理由自己就消失了。声明是否成立必须只取决于声明自身写了什么。
形状判定也不比登记表本身更严：`ServiceFamilyRegistry.register` 只要求能力标签是非空字符串，
声明侧要求同一件事，比它严会拒掉一个确实登记得上的族。存在性改由取用期回答。

**三、选中的实例名按关键字 `service_instance` 交给实现，且只对声明了该字段的扩展点出现。**
动作的调用形状是 `impl(context, **动作参数)`，用户在工作流节点上的选择就存在那份参数里，
宿主解析后按同一个键写回去；仪表盘的取数形状是 `get_dashboard(key, **kwargs)`，实参只在实现
签名接得住时才传，与既有的参数个数探测同一条兼容规则。没声明该字段的扩展点，两条调用链路
一字不改——这正是「新增字段不得让既有声明失效」的兑现方式：不是靠给新字段一个安全默认值，
而是让它整个不参与。

**四、失效提示另开一条，不并进 `absent_providers`。** 判据是用户在哪里看到它。
`GET /service/absent_providers` 回答的是「配置还在、提供方没了」，看的人是在设置页收拾服务
配置的管理员；被引用的实例消失回答的是「引用还在、被引用的实例没了」，看的人是在工作流
编辑器或仪表盘上的使用者。方向相反、页面不同、处置动作也不同，合并只会让两边都答不准。
但**记账口径一致**：同样只交稳定的成因代码不交文案，同样分开成因而不笼统答一个「不可用」
——族没登记、实例被删了、实例还在但停用了、实例在但类型不在收窄范围里，四者分别对应装回
扩展、重建配置、启用配置、改选一台类型对得上的。

未选实例时的裁决走 §7.2 同一条规则：有已启用的显式默认调用目标则用它，没有默认、默认已
停用、或默认被 `types` 收窄排除在外，一律报错并列出候选，绝不取第一个。只有一个候选也不
替用户挑——没有默认就是没有默认。登录认证族没有默认调用目标这个概念，该族一律要求显式指定。

实现收在 `app/runtime/extensions/admission/service_instance_requirement.py`，候选与已选实例的现状由
`GET /service/instance_candidates/{capability}` 交出。该端点只要管理权限而非超级管理员：它的
消费方是工作流编辑器，且候选只带身份与启用态、不带 `config` 载荷。

### 7.10 插件能 import 什么是一条独立规则，不并入依赖矩阵

宿主的包级依赖矩阵刻意跳过 `app/plugins/`，这条本身站得住：插件是第三方代码，宿主的内部
分层是宿主自己的组织方式，拿它去约束插件既管不着也没道理。但副作用是「插件该依赖什么」
整件事无人回答——插件 import 任何宿主内部路径，门禁一条都不会红。

两个原生参考实现各自独立撞上了同一堵墙：声明式注册是扩展面的主入口，存储契约按基类的
MRO 判定，登录入口列表承载着去歧义后的身份标识，三者在 SDK 里都没有出口，于是只能直接
import `app.runtime.extensions.*` 与 `app.modules._base.*`。宿主自己反而守着规矩绕行——
`app/runtime/extensions/admission/storage.py` 为了不造 `runtime → modules` 反向边，
改用 MRO 限定名字符串比对。宿主绕着走，插件无路可走，缺口就是这么显形的。

三处裁决：

**一、单立一条规则，不把插件纳入依赖矩阵。** 矩阵回答的是「宿主内部谁能依赖谁」，判据是
分层；插件这条回答的是「宿主对外承诺了什么」，判据是公开面。两者的判据不同、违反后的处置
也不同——宿主越界是改 import，插件越界往往意味着 SDK 缺东西，该补的是宿主的出口。混进同
一张表就会让「插件用了个没有出口的符号」被记成插件的错。

**二、公开面按「宿主自己不许用的那一面」定义，只有两条。** `app.sdk` 是唯一的插件门面，
宿主实现层反过来被禁止依赖它。`app.schemas` 是生成的惰性兼容聚合入口，宿主被禁止使用这个
聚合入口、必须走精确子模块，插件反过来只许用聚合入口——子模块的划分是宿主的内部组织，
聚合入口才是版本化的公开面。两条都不是新划的线，而是既有约束的另一半。插件包内导入照常；
跨插件导入不在公开面内，另一个插件装没装、是什么版本都不是本插件能假定的。

**三、门禁要指名道姓，报错本身就是改法。** 只说「越界了」等于把找出口的活推回给作者，而
作者恰恰是最不该知道宿主内部结构的人。SDK 导出快照同时是一张反查表，按 canonical 符号
倒查得到取用位置，于是每条违规都能给出「哪个文件哪一行、import 了什么、改用 SDK 的什么」。
查不到取用位置时提示的也不是「换个写法」，而是「SDK 未提供该出口，先补门面」——边界不因
为某个符号不在里面就放宽。

**四、门禁的对象是随仓入库的参考实现，不是磁盘上的 `app/plugins/`。** 那个目录同时是运行期
的插件安装目录，装在里面的第三方插件不是本仓的代码，且多半是靠兼容层工作的 v2 插件——按
v3 SDK 判它们越界，等于把 v2 生态当场判死，还会让门禁随开发机上装了什么插件而红，因环境
而红的规则很快就会被加上 skip。扫描范围因此按显式清单登记：参考实现是给社区照抄的范例，
「只用 SDK 也写得出来」由它们担保。显式清单的代价是新增参考实现要多改一处，而漏改的后果
不是报错、是这个插件悄悄不受保护，故另立一条断言——git 索引里 `app/plugins/` 下的插件必须
与清单逐个对上；git 判不了时该条跳过，扫描范围本身不受影响。

`_PluginBase` 原样从 SDK 导出，不逐层挑拣。它混着冻结契约、扩展点与内部实现三层，挑拣要
先划界，而这条界划错的代价是存量插件失效。改为快照登记它的公开面：类成员与实例属性分列，
增删都要显式改一次登记，于是三层的漂移是被评审出来的，而不是随基类改动悄悄发生。

存储后端契约 `StorageBase` 现居 `app.modules._base.storage`，SDK 为它开的出口是矩阵上的一条
记账负债而非默许——契约迁出 `app.modules` 后，SDK 与 `app.runtime` 两边都能直接 import，
上面那处 MRO 字符串比对也一并退役。

门禁在 `tests/test_plugin_import_boundary.py`，导出快照在 `app/sdk/_exports.py`。

## 8. 明确不做

- 插件侧的 per-plugin 能力清单，理由见 §2.3
- 打开 `capability.toml` 的 `depends_on` 字段：那是内建模块之间的依赖，与插件间依赖是两回事，不共用同一套字段
- 为「同一能力多实现」预设仲裁策略：现有的优先级加单播首个认领已经够用，未出现真实冲突前不加抽象

## 9. 已知风险

**能力发现流程对异常输入一律抛错。** `CapabilityRegistry.discover` 遇到「声明根没有清单」「清单非法」「capability id 重复」都会抛 `CapabilityManifestError`。在只服务 `app/modules` 的前提下这是正确设计——那里每个包都必须有合法清单。

但这意味着：**任何时候把这套发现流程指向宿主控制不了的目录，都必须先做隔离**。已验证的三种击穿输入及其后果记录在 `docs/plugin-native-capability-poc.md`。

**索引由插件作者维护，可能过期或不实。** 不应把它当作运行期真相；运行期真相由 `provides_*` 的注册结果确定。
